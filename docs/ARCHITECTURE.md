# 設計メモ（ポートフォリオ抜粋）

```text
[予約者] → [代理参加・友達紹介]
              ↓
        [ゲスト仮IDの検証] ──→ [仮予約 / 履歴]
              ↓
          [本人登録]
              ↓
       [同名候補の抽出]（この時点では未確定）
              ↓
         [管理者による確認]
              ↓
       [人物IDと戦績の照合]

[キャンセル待ち] → [繰り上げ候補] → [通知先IDの突合] → [通知]
```

## この抜粋で表した設計方針

1. **名前をキーにしない**：同姓同名でも別人として扱う。不完全な照合結果は保留する。
2. **紹介者と参加者を分離**：友達の参加履歴が紹介者の戦績に加算されないようにする。
3. **原本は保全**：試合記録そのものを書き換えず、表示・集計時に照合を判断する。
4. **通知の誤配送を避ける**：IDと氏名の明確な矛盾があれば配信しない。
5. **外部依存を分離**：キャンセル待ちのビジネスロジックはDB/通知依存を注入してテストする。

## 対象外

フルUI、本番Firebase設定、データベース実体、運用者権限、実デバイスのPWA設定などは含めていません。これらは本番プロジェクトに存在する別領域です。
